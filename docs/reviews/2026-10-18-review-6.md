## Review of the new work

### Rate limits

The core algorithm is a real sliding window: accepted timestamps are retained for the longest rule, shorter windows count only their own timestamps, exact-boundary entries expire, and rejected requests do not extend the window. Account keys derive from verified JWT subjects. FastAPI can reuse the same auth dependency for the handler and limit dependency. The lock covers checking and appending: a controlled 300-call/32-thread run admitted exactly **60**, rejected **240**, with a 60-request rule. Taking the timestamp inside that lock would also preserve deque ordering when threads are descheduled between clock sampling and insertion.

The four committed rate tests passed, but do not cover simultaneous saturation of multiple windows, concurrency, or memory cleanup. **Retry-After can be too short: R6-L01.** The global exception handler preserves its header. Live, on A only, five DELETE `/api/account` requests with `confirm: "KEEP"` returned 422; request six returned **429, Retry-After: 60**. No deletion was attempted by those invalid confirmations, and the limit had expired before the later real deletion.

All explicit write routes have a limit. Public reads and expensive authenticated reads do **not** all have limits: **R6-M03**. For ordinary polling, 60/account/minute is generous: a continuously visible tab polls about four times/minute, a hidden tab about once/minute. Three to five tabs ordinarily fit comfortably; fifteen simultaneously visible tabs consume the whole allowance before startup/actions/fresh polls. Limits are shared across games. The UI currently turns poll 429s into a generic connection warning and retries on its regular schedule, rather than honoring Retry-After.

Memory is **not hard-bounded at 50,000 keys**. An offline run retained **50,002 active keys**. Below the threshold, idle identities remain; above it, every accepted request scans the entire dictionary under the global lock, while keys used within the last hour survive regardless of their rule's shorter window. Per-key histories are bounded by configured request caps, but identity count is not. This is a capacity/abuse-hardening limitation for the present small deployment: add expiry-based eviction on a bounded schedule and an explicit capacity policy. State also resets on deploy/restart and is not shared across workers, as the code documents.

**IP trust:** `main.py:422` trusts CF-Connecting-IP, then the leftmost X-Forwarded-For value, without validating the address or proxy. A direct/local caller can select arbitrary buckets; the existing IP test itself demonstrates that behavior. That does **not** prove a bypass of the deployed Cloudflare path: [Render documents that inbound web traffic traverses Cloudflare](https://render.com/articles/how-render-handles-ddos-attacks), and [Cloudflare documents CF-Connecting-IP replacement and appending to pre-existing X-Forwarded-For](https://developers.cloudflare.com/fundamentals/reference/http-headers/). The preferred CF header is reasonable under that deployment assumption; trusting the first XFF element is unsafe on a path that merely appends to attacker-supplied XFF. Document/enforce the trusted ingress, validate/normalize IPs, and resolve a trusted proxy chain on fallback. I did not establish production header spoofing or flood a public-IP bucket. Header spoofing would not change JWT identity or bypass the per-account write limits.

## New findings

### R6-H01 — High: both CI jobs can succeed when pytest fails

**Location:** `.github/workflows/tests.yml:24`, `:67` and `:69`.

Neither workflow nor step selects `shell: bash` or enables `pipefail`. GitHub's unspecified Linux shell is `bash -e {0}`; its explicit Bash option adds pipefail. See [GitHub's shell documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsshell).

**Repro/evidence:** pytest exits nonzero on an assertion/collection failure, but `pytest | tee out.txt` takes tee's successful status. The following annotation succeeds too. In the integration job, output containing FAILED and no SKIPPED also passes the final negative grep. A local Git Bash reproduction with a failing producer through tee, a subsequent annotation, and that skip predicate returned **0** under `bash -e`; the same reproduction returned **1** with pipefail enabled. Thus even the mutations above could be reported in a green CI job.

**Suggested fix:** set `defaults.run.shell: bash` (or explicit `set -o pipefail`) for both jobs, or capture and propagate pytest's pipeline status deliberately. Preserve skip detection in addition. Verify the workflow with an intentional failing test and collection failure, not only a successful run. This finding concerns CI failure reporting; the previously open Render deploy-after-CI setting is separate.

### R6-M01 — Medium: an in-flight save can recreate public data after successful account deletion

**Location:** `main.py:711`, `:1203`; `db/migrations/003_delete_account_data.sql:19`; `tests/integration/schema.sql:45`, `:63`, `:76`.

**Repro:** in memory, real API handlers and the fake DB: start an edit for an existing account; pause immediately before its profiles upsert executes, after it has read the reserved username. Complete DELETE `/api/account`: **200 deleted**, Auth user and accounts row gone. Resume the upsert: **200 saved**. Final state: Auth user absent, accounts absent, **one profile present**. `/profile-full?username=qaoffline` returned it and another test player's `/api/match` listed `qaoffline`.

The supplied production-schema copy permits this insert: `profiles.user_id` has no FK. The deletion function's transaction cannot reject a later independent write. Similar late likes/blocks are not protected by user FKs either. A stale access token also remains signature-valid until expiry, as [Supabase documents](https://supabase.com/docs/guides/auth/managing-user-data); deleting the Auth user alone does not invalidate this application's offline JWT check. This reproduction was **offline**, not an attempt to leave orphan data in production.

**Suggested fix:** enforce lifecycle integrity in the database: user FKs with suitable delete behavior on every referencing table, plus transactionally coordinated account-deletion/writer checks or a deletion tombstone. Handle legacy/orphan rows before adding constraints. An application existence check alone still races. Add a real-Postgres late-save/late-social-write test and retain the normal live deletion test.

### R6-M02 — Medium: older avatar propagation can overwrite a newer completed choice

**Location:** `main.py:721`–`:723`, `:1188`; `db/migrations/004_set_profile_avatar.sql:20`.

**Repro 1:** delay the synchronization of PUT avatar-3; while delayed, complete a second ordinary PUT avatar-5 including its sync; resume avatar-3's sync. Both PUTs return **200**, both responses report account avatar-5, but GET own-profile reports **avatar-3**. Fields stay intact; matching/squad avatars now disagree with the account/public profile.

**Repro 2, specifically challenging the R5 reverse-race claim:** a profile save reads the initial avatar; avatar-3 is saved while it is in flight; the new post-upsert reread captures avatar-3; complete PUT avatar-5 before the reread's value is applied; resume the save's sync. POST returns **200**; account **avatar-5**, game profile **avatar-3**, edited Wingman/Silver fields preserved. Both reproductions used actual current API handlers with deterministic in-memory barriers.

**Suggested fix:** make one database value/version authoritative for account avatar and profile propagation, with conditional updates rejecting older versions; alternatively stop copying it into profiles. A second unconditional Auth read merely moves the race. Serialize all relevant writers only if that serialization covers profile saves, avatar updates and the deployment's worker model. Add both ordering tests to the real database layer.

### R6-M03 — Medium: unbounded read routes bypass the intended resource protection

### R6-L01 — Low: Retry-After ignores a longer simultaneously saturated rule

**Location:** `main.py:411`–`:415`.

## Disagreements with Claude

1. **Accept all five narrow R5 fixes; reject “the reverse race ... is closed too.”** The new reread closes the committed test's particular ordering, but R6-M02 shows a newer choice lost after that reread. An atomic JSON-path update preserves game fields; it does not make distributed account/profile state linearizable.
2. **Reject the implication that green CI now proves the real-database layer passed.** The job is worthwhile and the schema is materially stronger than a fake, but R6-H01 allows failing pytest to be green. Local integration execution remained unavailable, and a copy labeled production is not an independently checked live catalog.
3. **Reject “every browser test now fails on any uncaught page error” and “every page ... readiness ... run by its own JS” as universal claims.** Mobile contexts bypass that fixture, and legal readiness uses static content. The new mutations provide direct counterexamples. Accept the strengthened Skip/blank-page checks, real SDK load test, and narrowed wrong-account navigation handling.
4. **Qualify “per-IP ... on every ... public read.”** Public profile HTML/deep health are concrete unbounded DB paths, and authenticated social aliases evade poll's limit. The write-route part is correct. Ordinary several-tab polling is unlikely to hit 60/minute; my criticism is incomplete protection and response handling, not that three tabs necessarily break it.
5. **Accept transactional data deletion, not a complete deletion lifecycle.** Migration 003 is a valid improvement. It neither coordinates late writers nor fixes the already acknowledged separate Auth-failure recovery/support gap. Known metadata/referral races, independent report retention/moderation, draft legal/support and deploy-after-CI work remain open; a successful ordinary live flow does not close them.

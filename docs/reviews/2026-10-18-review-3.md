## New findings and remaining defects

### R3-H01 — High: a 401 refresh can replay A's mutation using B's token

**Location:** `static/js/ui.js:124`, `static/js/ui.js:140`, `static/js/ui.js:49`.

**Reproduction, current-source VM:**

1. Set page owner/token to A and start a profile POST containing A's private form data.
2. Return 401 from the first send. During refresh, deliver `SIGNED_IN` for B and return B's access token.
3. The auth callback requests reload, but execution continues: `authFetch` retries the original body with B's token.

Captured sends were `{owner:A, body:A_PRIVATE_FORM}` followed by `{owner:B, body:A_PRIVATE_FORM}`; reload was also requested. The pre-send guard does not protect the retry. This was a deterministic offline reproduction, not a cross-account write on production. Live tests separately established that account mutations follow the supplied user's token, as intended by the backend.

**Impact:** A's Discord/location/profile values can be copied into B's account during session refresh/account switching. Requesting navigation does not cancel the currently executing async function.

**Suggested fix:** capture the owner/session generation at operation start; check both the generation and the returned token's uid after every auth await and immediately before **every** send, including retries. Throw `AUTH_SWITCHED` rather than retry when ownership changed. Share this implementation across all authenticated pages. Add a test where the refresh callback itself changes accounts before the refresh promise resolves.

### R3-H02 — High: Settings and profile editing still act on another account after a tab switch

**Location:** `static/js/profile.js:47`, `static/js/profile.js:237`, `static/js/profile.js:262`; `static/js/settings.js:23`, `static/js/settings.js:130`.

**Reproduction:** open A's owner profile editor or Settings; sign in as B in another tab; use the still-open A page. These pages retain A's account/UI but read the current `pm_access_token` from shared storage for each action. Neither has `/app`'s page uid guard or account-change listener. The profile ownership flag is set once at `profile.js:331`.

Current-source VM calls on **both** pages sent the old edit body with `Authorization: Bearer TOKEN_B`. The profile's real `saveEdit` uses that helper for PUT `/api/account`; `removeGame` does likewise for DELETE `/api/profile`. Settings' real delete flow uses its helper for DELETE `/api/account` with no target-account binding.

**Impact:** saving A's editor modifies B; removing A's displayed game removes B's corresponding game; confirming deletion on a Settings page still displaying A can delete B. These consequences follow directly from the request targets and backend JWT identity; the destructive wrong-account scenario was not attempted live. All live deletions deliberately used the intended test account's own token.

**Suggested fix:** apply the owner/session guard to profile and Settings, including refresh retries and response application. Invalidate old DOM/actions as soon as auth changes. Bind deletion confirmation to the page's captured uid, and reject submission if it differs from the current session. Cover A→logout→B in a second tab on all three authenticated surfaces.

### R3-H03 — High: separate block/contact snapshots can reveal a new contact written after blocking

**Location:** `main.py:931`, `main.py:932`, `main.py:937`, `main.py:945`.

**Controlled fake-DB reproduction:**

1. A and B are mutual. A's poll reads mutual likes, then reads an empty block set.
2. B's block of A commits.
3. B saves a new private IGN, `NEW_AFTER_BLOCK`.
4. The poll's subsequent profiles query sees that new value and returns it to A in `squadmates`.

The current function returned `NEW_AFTER_BLOCK`. At no instant was **that contact value** available while the pair was unblocked. This disproves Claude's bound that the worst case only repeats contact the viewer already had. The reproduction used RAM only; I did not attempt to schedule this race against production. Normal blocking and contact hiding passed live.

**Suggested fix:** project private squad contact in a single SQL statement joining both like directions, the game's profiles and a bidirectional `NOT EXISTS` block check. Expose it through a restricted view/query or a narrowly scoped RPC. An RPC is an implementation option; the requirement is a shared authorization-and-data snapshot. Merely issuing a final separate blocks check can construct the reverse inconsistency and is not equivalent.

### R3-M01 — Medium: generation protection still misses error, timer and scan-recovery paths

**Location:** `static/js/ui.js:474`, `static/js/ui.js:752`, `static/js/ui.js:835`, `static/js/ui.js:841`, `static/js/ui.js:844`, `static/js/ui.js:857`, `static/js/ui.js:949`, `static/js/ui.js:1002`.

Three independent VM reproductions:

- Start a CS2 scan, switch to GTA, reject the old scan: its catch calls the idle renderer for **GTA**, clears loading and displays `OLD CS2 FAILURE`. A rejected old profile save similarly displays its error in the new game. Success checks do not protect catches/finally blocks.
- Start Skip or Like, switch games before a new match list is received, then run the old timer. Selection increments `gen` but not `deck`; the timer only checks deck/index. Both timers advanced the new game's index from 0 to 1 and rendered under GTA. This is possible while the new game is still loading, fails to load, or has no profile.
- Start a CS2 scan, select GTA and then CS2 before it resolves. The two automatic new scans are suppressed by the global in-flight/loading flags. The original response is correctly rejected by generation, but `finally` compares only the game string, now CS2 again, so no replacement scan runs. Result: zero matches, one request total, and no active scan.

**Suggested fix:** invalidate deck generation on selection/account change and list mutations; capture/check generation in every success/error/finally/timer continuation. Release only the loading state owned by that request. Queue the current generation's scan when an obsolete scan finishes, even if its game id equals the current one. Check again after `await refreshStats()` and other secondary awaits. Add deterministic tests for rejected requests and A→B→A, not only successful late responses.

### R3-M02 — Medium: Pass removal lets an existing swipe timer skip the next player

**Location:** `static/js/ui.js:1189`, `static/js/ui.js:1233`, `static/js/ui.js:947`.

**Reproduction:** deck `[Bob, Carol, Dave]`, index 0. Start Skip on Bob; before its 280 ms timer fires, Pass Bob in “Liked you.” Pass now removes Bob, yielding `[Carol, Dave]`, still index 0. Because `removeFromDeck` leaves `state.deck` unchanged, Bob's timer passes its guards and advances to index 1: **Dave**. Carol was silently skipped without being shown or recorded as skipped.

This was reproduced with the current frontend functions in the VM. Normal Pass now works; this is specifically an interaction regression introduced by changing the deck in place.

**Suggested fix:** bump deck generation whenever membership/order changes and coordinate animation/in-flight locks with removal. A timer must refer to the actual card identity as well as its generation, not a reusable numeric index. Test Pass/Like back/Block while a swipe is pending.

### R3-M03 — Medium: the combined likes query halves the social row budget and loses mutuals

**Location:** `main.py:252`, `main.py:931`; related `tests/fakedb.py:146`.

The single OR query has no pagination/explicit bound handling. Under the 1,000-row PostgREST cap modeled by the project, 600 outgoing likes followed by the corresponding 600 incoming likes return only the first 1,000 rows. The current `social_state` returned **400 mutual squadmates instead of 600**, falsely treating the other 200 as pending. Before this change, each directional query could return all 600 rows.

This was reproduced on the capped fake only; it is a scale regression, not a claim that production currently has this volume or that its dashboard limit was independently inspected. Even 501 mutual pairs exceed a 1,000-row combined budget. Without ordering, the missing relationships are not a stable selection.

**Suggested fix:** classify mutual/pending/incoming in SQL before pagination, return explicit page/cursor metadata and totals, and page the user-visible lists. Do not fix this by independently paging the two sides and reintroducing incompatible authorization snapshots. The contact query proposed in R3-H03 addresses both problems when designed with pagination.

### R3-L01 — Low: forced logout still loses the requested game before selection

**Location:** `static/js/ui.js:118`, `static/js/ui.js:1627`, `static/js/ui.js:1635`.

**Reproduction:** request `/app?game=cs2` with a rejected stored session. Initial `loadMyGames` runs before `selectGame`, so `state.game` is null. `clearAuthAndRedirect` uses only that value and sends the user to `/`. VM reproduced exactly that redirect with the desired query present.

**Suggested fix:** capture/validate the requested game at startup, and use `state.game || requestedGame` for auth redirects. Retain the existing game-id validation. Test invalid-session startup separately from logout after selecting a game.

## Disagreements with Claude

**R2-H01: accept the one-query likes fix; reject the stated bound on the remaining race.** Claude is correct that the OR query prevents constructing mutual likes from two different statements. An RPC is not inherently necessary for that narrower repair. PostgREST executes requests inside transactions, and PostgreSQL Read Committed gives an ordinary SELECT a statement snapshot. [PostgREST transaction documentation](https://docs.postgrest.org/en/stable/references/transactions.html), [PostgreSQL isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html).

But that statement snapshot does not cover the later blocks/profiles requests. R3-H03 returns a newly created private value after a block, rather than merely repeating old known contact. There is also no measured or enforced “~100 ms” bound: database/network waits can extend the interval. I recommend one contact-bearing SQL projection combining mutual authorization, block exclusion and profile data. A service-only view or narrowly granted SQL RPC is a concrete, small solution; a broad backend rewrite is unnecessary. Review grants/RLS deliberately, and derive the viewer from verified server identity. A sequence of separate reads is not an equivalent fix.

**D4: accept fake tests as the fast layer; reject absence of local Node as a reason to omit CI behavior tests.** The workflow already invokes Node for syntax checks. Add a `tests/frontend/` behavior harness that executes the real JS with deferred fetch responses, synthetic auth events, fake storage and controllable timers. Start with R3-H01/H02, generation error paths, Pass during swipe and fresh-poll waiting. A VM harness is suitable for those deterministic invariants; supplement it with a small browser smoke suite for DOM/render/CSP behavior. It is not a replacement for browser testing, and stubs should be limited to IO/render boundaries rather than duplicating the implementation.

**A separate Postgres environment is a requirement to provision, not a reason to close integration coverage as unnecessary.** GitHub Actions supports disposable Postgres service containers. [GitHub's official Postgres service example](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers). For this app, add a disposable PostgREST layer or local Supabase stack as well, so tests exercise actual REST upsert semantics, constraints, RLS and row limits. A Postgres-only test does not prove PostgREST request behavior. Apply a self-contained schema in CI; migration 001 alone assumes earlier tables/auth schema already exist. Never configure this job with production credentials. Test competing username claims with two DB connections, monotonic report/unblock behavior, the contact projection and the capped social query. The sequential test at `tests/test_review2.py:29` is a useful normal-state test, but it does not itself inject a write between poll reads.

**M03: accept the current atomic monotonic-block repair; accept deferring a separate reports table only as an explicit product limitation.** A separate reports table is not needed to prevent plain block/unblock from clearing `reported=true`; the new conditional writes are a good smaller fix, and the live race passed. However, reports still share a replaceable single reason and are explicitly deleted when either account is deleted (`main.py:1152`). They are not an independent moderation record. If the product promises investigation/history, add append-only report events with reporter/subject references or retained snapshots, timestamps, reason and moderation status, under a defined retention/deletion policy. Keep user-controlled blocking separate from case history. Do not imply a staffed moderation service while there is no queue/contact path. This is an acknowledged remaining requirement, not a newly discovered failure of the fixed unblock condition.

I accept keeping already-mutual squads after platform/edition/server changes, the cached exact-count implementation for the current size, and the narrower Escape/CSP changes. I do not accept “all R2 findings fixed” as an accurate overall status while the account/session and contact-snapshot counterexamples above remain.

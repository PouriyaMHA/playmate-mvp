## Migration 005 review

**Locking and avatar writes.** `FOR UPDATE` in 005:33 is correctly placed before reading/copying the avatar. A waiting copy reads the updated row after the competing transaction commits under the normal read-committed behavior. `set_account_avatar` holds the account lock while synchronizing profiles, so two calls for the same existing account queue rather than applying stale values later. JSON changes touch only `game_meta.avatar`; game fields survive. Different accounts need not serialize against each other. These semantics match [PostgreSQL's row-lock documentation](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS).

There are two qualifications. First, a nonexistent row provides no serialization point (R7-M01). Second, the new account → profiles lock order conflicts with migration 003's profiles → account deletion order (R7-M02). The ordinary profile upsert is also a separate committed operation before `sync_profile_avatar` (`main.py:761`, `:773`); this is final reconciliation after a successful request, not one transaction covering the entire profile save. An interrupted/failed reconciliation can leave a stale copy until another synchronization. The old migration-004 `set_profile_avatar` RPC remains executable by `service_role` and bypasses the new authority; current application code no longer calls it, but retire or redefine it to prevent future accidental use.

**Cascade scope.** The new references point from `profiles.user_id`, both like endpoints and both block endpoints **to `auth.users.id`**. Migration 001 already gave `accounts.user_id` that parent. Therefore deleting a game profile, like, block or account-reservation row does **not** cascade upward into Auth or sideways into another player's profiles. Deleting an Auth user now removes their profiles and any relationship involving them, including a block/report authored by somebody else. That latter loss was already explicit in `delete_account_data` and the acknowledged report-retention gap; 005 also applies it to deletion through Supabase Auth/admin tools. Operators must treat Auth deletion as deletion of PlayMate data, not just disabling login. This is the direction of [PostgreSQL's ON DELETE CASCADE](https://www.postgresql.org/docs/16/ddl-constraints.html#DDL-CONSTRAINTS-FK), and Supabase recommends linking application user data to Auth IDs with that lifecycle in its [user-management guidance](https://supabase.com/docs/guides/auth/managing-user-data).

The FKs close the late-writer problem: a child committed before the Auth deletion is cascaded; one that loses that race cannot reference the deleted parent. Existing application writes supply IDs. Nullable legacy profile/like IDs are still permitted by the schema, so this is not a cleanup/NOT NULL migration for historical anonymous rows. Live A deletion left **B's two own profiles intact** while removing their shared likes/report. I did not invoke an admin Auth deletion in production; the API deletion also runs the explicit data RPC first, so the live result alone does not isolate the cascade. The committed integration test does isolate it.

**Backfill and deployment.** 005:16–19 copies Auth metadata into `accounts.avatar` for currently null accounts. It does **not** reconcile historical drift in `profiles.game_meta.avatar`. The final `count(avatar)` query measures account population, not agreement between account/profile copies. Existing drift needs a deliberate reconciliation and an equality check. Also, null is both “not backfilled” and the legitimate “initial/no avatar” value: rerunning the migration can reimport an old nonempty Auth value if the two stores have diverged. Do not describe that as unconditional semantic idempotence. No such production mismatch was established here. The migration transaction makes its DDL/backfill/grants all-or-nothing, but takes table locks and validates existing FK data; suitable for the present small installation, not an online large-table rollout. Constraint guards check `conname` globally rather than the table/schema/definition; future drift checks should verify the actual relationships, not merely those names.

**Grants and live refusal.** Both functions are invoker functions with a fixed search path, no dynamic SQL, and explicit revocation from PUBLIC/anon/authenticated followed by a `service_role` grant. I called each with the anon key and with A's genuine logged-in token, using only A's ID:

The rejected setter requested the initial/no-avatar value before A had a profile; no other player's ID was used.

## New findings

### R7-M01 — Medium: first username claim can overwrite a newer successful avatar choice

**Location:** `main.py:189–198`, `:317–319`, `:1244–1248`; `db/migrations/005_account_avatar_and_user_fks.sql:33–35`, `:54–55`.

**Repro:** deterministic in-memory interleaving using the actual current API handlers and fake database, without changing any file:

1. Auth user exists; no `accounts` row. PUT avatar-3 succeeds, as supported by `test_first_profile_carries_an_avatar_chosen_before_it`.
2. First POST profile reaches `claim_username`; its INSERT payload has captured avatar-3. Pause immediately before executing the account INSERT.
3. Complete PUT avatar-5. It writes Auth metadata, updates **zero** account rows, synchronizes **zero** rows, and returns **200, avatar-5**.
4. Resume the older INSERT and profile save. POST returns **200**. GET account and own-profile now both say **avatar-3**; Auth metadata still says **avatar-5**.

This is a lost completed choice, not merely an inconsistent read while propagation is running. The new source of truth is seeded with an old value after the successful update. Locking a missing account row does not coordinate creation. I did not attempt to force a server-internal barrier on production.

**Suggested fix:** ensure there is a database row/serialization point before allowing avatar writes, and coordinate its initialization with username claim. A simple product-compatible alternative is to reject pre-claim avatar updates until the account is claimed; the public editor already requires a claimed profile. If pre-profile avatar selection must remain supported, store it in an always-present per-user settings row and claim against that same authority transactionally. Add this exact missing-row interleaving to API and real-Postgres tests; the existing sequential pre-profile test cannot detect it.

### R7-M02 — Medium: avatar synchronization and account deletion acquire locks in opposite orders

**Location:** `db/migrations/005_account_avatar_and_user_fks.sql:33–40`, `:54–55`; `db/migrations/003_delete_account_data.sql:23–25`; callers `main.py:1247`, `:1262`.

**Repro schedule, derived from the SQL:** an existing account/profile has avatar-3. In two transactions, pause deletion after deleting its profile but before deleting its account row. Start `set_account_avatar(uid, 'avatar-5')`: it locks the account, then waits while updating the profile held by deletion. Let deletion continue to its account DELETE: it waits for the avatar transaction. There is now a cycle, **profile → account → profile**. PostgreSQL resolves this by aborting one transaction; the API does not specifically retry this case. Two tabs/devices deleting and editing the same account can therefore get a failed deletion/save. Rollback prevents partial changes inside the individual RPC; this is not a claim that a deadlock commits half a deletion.

**Evidence limit:** this is a concrete lock-order review finding, **not** a locally executed Postgres or live deadlock reproduction. PostgreSQL documents both the conflicting locks and the need for consistent acquisition order in its [deadlock guidance](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-DEADLOCKS). The committed 005 concurrency test covers avatar-versus-copy and avatar-versus-avatar, not deletion-versus-avatar.

**Suggested fix:** make `delete_account_data` take the same account lock before its child deletions; review that order alongside Auth cascades and any future transaction touching multiple users. Add a deterministic two-connection test for this schedule and a bounded retry for retryable deadlock errors where appropriate. No production deadlock stress test is needed to establish the inverted order.

### R7-L01 — Low: poll 429 still displays a false connection warning

**Location:** `static/js/ui.js:1080`, `:1092–1094`.

**Live repro:** exhaust A's shared social budget using its own no-profile-game polls, confirm all aliases return 429, then load A's existing CS2 app. The orange **“Connection issue. Some features may not work.”** banner appears (`display:flex`). The quota response had a valid Retry-After, and the rest of the app loaded normally.

**Cause:** `startSocial` uses `throw new Error('poll failed: 429')`; unlike `apiJson`, it never attaches `err.status`. The new `err.status !== 429` catch condition is therefore true. Merely adding the condition did not implement the intended behavior.

**Suggested fix:** handle 429 before the generic throw, or attach the HTTP status consistently; delay subsequent polls until Retry-After. Preserve the distinction between unavailable social data and an actually empty squad. Add a real-browser 429-response regression asserting no network warning and a later successful refresh.

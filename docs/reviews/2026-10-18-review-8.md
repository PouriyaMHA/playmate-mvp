## Feature review: Like / Like back from a public profile

Its response contains the target name, self flag and game states; it does not serialize profile rows or contacts. Selecting `*` at `:1348` is unnecessary internal access to contact columns; use a minimal projection when touching this code, but I found no outgoing contact leak from it.

Live A and B became mutual while C's response for either target still described **C's own** relationship. B blocking A in GTA made both directions of `/api/relationship` return **404**, and B's browser displayed **Player not found** for A. C's response disclosed no A–B block or A–B like state. A blocked like returned **403**. Relationship payloads contained neither B's unique Steam name nor Discord, including for A; mutual contact was available through the existing authorized Squad poll instead. Public squads intentionally expose mutual squad membership under the existing product policy; this endpoint adds no third-party one-way-like lookup.

## New findings

### R8-M01 — Medium: a successful profile like can leave the enabled Like button on screen

**Location:** `static/js/profile.js:171–176`, `:179–193`.

**Live repro:** open A's profile as compatible C with state `none`. Exhaust C's relationship-read budget using its own self-relationship reads, leaving its independent like budget available. Click Like. The write succeeds and the success toast appears, but the following relationship read returns **429**. `loadRelationship` silently retains the old `page.rel`; `renderTab()` creates another **enabled Like button**. C's real poll showed A in `pending`, proving the action was stored. I also reproduced the same UI behavior with a browser-routed relationship 429 after a real successful write, before the live-quota reproduction.

The visible control contradicts the completed action and invites repeated submissions. Server idempotence prevents duplicate relationships, but does not repair the UI or avoid further quota consumption. Initial relationship failures likewise remove the entire action without an explanation or retry.

**Suggested fix:** apply the successful write's `mutual` result to the local game state immediately and render it. Treat the follow-up read as reconciliation: handle non-OK responses explicitly, offer retry and respect Retry-After. A blocked/not-found result should invalidate the relevant profile/actions rather than silently retaining them. Add a Chromium regression for **POST success → GET 429/500**, asserting the waiting/mutual state and no enabled duplicate Like action.

### R8-L01 — Low: “In your squad — open it” opens Match on a phone

**Location:** `static/js/profile.js:159`, `:164`; `ui.html:14`; `static/js/ui.js:1664–1670`.

**Live repro:** after B likes A back, tap the mutual control on B's 375 px public-profile view of A. The destination is `/app?game=cs2`; `body[data-view]` remains **`match`** and `#squad-panel` is **not visible**. The user sees another discovery card rather than the promised matched person's contact. Desktop has the Squad column, but still does not focus the target.

**Suggested fix:** support a validated Squad destination, for example a tab parameter handled after game load, and select/scroll to the relevant teammate. Make the mutual link use it. Add a phone browser assertion that this click exposes the actual Squad/contact panel.

### R8-L02 — Low: the profile relationship stays stale after the other player acts

**Location:** `static/js/profile.js:171–176`, `:189–190`, `:350–351`, `:410–411`.

**Live repro:** leave B's view of A open while A likes B: B still sees ordinary Like. Refresh B and like back: A's still-open page continues saying **“waiting for them”** although its relationship API now says `mutual`. Separately, after loading a mutual view, B unmatches through its own API; A still sees **“In your squad”** even after switching Achievements → Games, while a fresh API read says `none`.

Only initialization and the viewer's own successful like load this data. There is no focus/visibility refresh or explicit relationship-refresh affordance. This is especially misleading when the page explicitly asks the user to wait for a like back. The anonymous-to-login case described above is another missing lifecycle transition; its storage listener at `:57–58` does not reload an unpinned anonymous page.

**Suggested fix:** revalidate on return to the page and relevant tab activation, with a visible retry/refresh path; if the page promises live waiting, add bounded polling while visible. Re-evaluate account/owner state on anonymous-to-authenticated transitions as well. Clear invalidated state on 404 and guard responses by the current account. Add browser cases for incoming like, mutual, unmatch and first login without manually reloading the tested page.

### R8-L03 — Low: a first-time signed-in viewer never gets the no-profile guidance

**Location:** `static/js/profile.js:172`, `:166`.

**Live repro:** C signs up but has not saved its first game profile. C's relationship API for A returns **`cs2: no_profile`**. The browser shows neither Like nor **“Add Counter-Strike 2 to your games to like them”**, because `loadRelationship` exits when `page.account.username` is null. After C claims a username through its first profile, the normal controls appear. The intended no-profile branch therefore misses precisely the newest signed-in players.

**Suggested fix:** allow an authenticated unclaimed viewer to load relationship states; the API already supports it. Show the first-profile CTA and preserve the target/game through setup so the viewer can return to this person. Test a fresh Auth user with zero game profiles, not only a claimed account missing one additional game.

## Migration 002 and browser access

**The function as written is a valid shared-snapshot solution.** Its SQL body is one `WITH ... SELECT jsonb_build_object(...)` statement; the aggregates and subqueries belong to that statement. `language sql stable` is appropriate for a read-only function: PostgreSQL documents that STABLE functions use the calling query's snapshot. CTE materialization versus inlining does not turn this into independent snapshots. [PostgreSQL function volatility](https://www.postgresql.org/docs/current/xfunc-volatility.html). PostgREST executes the RPC within a request transaction. [PostgREST transactions](https://docs.postgrest.org/en/stable/references/transactions.html).

- **NULLs / NOT IN:** line 35 explicitly removes NULL `other` values from the right-hand side. A legacy block involving the viewer and a NULL counterpart therefore cannot poison the anti-filter and hide every profile. NULL profile user IDs do not satisfy membership. A NULL like counterpart cannot introduce a different user's profile. Empty aggregates become `[]`, not JSON null. A NULL viewer matches no likes/blocks; NULL `g` matches no game but still returns that viewer's global block IDs. The API supplies verified UUID identity and normalized game IDs. These edge cases were reasoned from the SQL, not inserted into production. [PostgreSQL NULL comparison semantics](https://www.postgresql.org/docs/current/functions-comparisons.html).
- **Blocks across games:** the block CTE deliberately has **no game condition** and tests both directions. Profiles are filtered by the requested game and the same CTE. The live GTA-block/CS2-poll test passed in both directions.
- **`with_profiles`:** omitted means true; false, or explicitly NULL, suppresses profile aggregation while retaining likes and blocks. `like_maps` and `mutual_ids` pass false (`main.py:264`, `:270`); their live public counts/squads worked. The flag is an output option, not authorization. With true, nonmutual related players' full rows also reach the trusted server; `social_state` only attaches contact fields for mutuals and whitelists pending/incoming output. Live nonmutual and public responses contained no contact fields.
- **Row cap:** the aggregate is one scalar JSON result, so REST's row cap cannot cut 1,200 embedded likes into 1,000 rows. JSON size, query time and unbounded list rendering remain scaling limits. `/profile-squad` still makes its own ordinary profile-row query (`main.py:1241`); this change does not promise unlimited public-list pagination.
- **Privilege boundary:** lines 40–41 revoke execution from PUBLIC, anon and authenticated, granting service_role. There is no SECURITY DEFINER declaration; the function uses invoker privileges. The arbitrary `viewer` argument is acceptable only behind this boundary and the backend's verified identity. Neither browser role can choose a viewer through this RPC.

Actual requests to **`POST https://fffejwdrqhizgxpjacgn.supabase.co/rest/v1/rpc/social_snapshot`** supplied the public frontend `apikey`, an explicit viewer UUID belonging to another disposable account, `g="cs2"`, and each flag value:

| Authorization bearer | `with_profiles` | Live response |
|---|---|---|
| Public anon key | true | **401**, `42501`, `permission denied for function social_snapshot` |
| Public anon key | false | **401**, same denial |
| Logged-in disposable user's access token | true | **403**, `42501`, same denial |
| Logged-in disposable user's access token | false | **403**, same denial |

No service key, SQL execution, schema mutation or direct table write was used. I did not independently inspect deployed function text/catalog ACLs or run a disposable PostgreSQL instance; live API behavior and these denials corroborate the migration, without attesting its exact deployed definition.

## New findings and remaining defects

### R4-M01 — Medium: public squad browsing ignores the viewer's blocks

**Location:** `main.py:1233`, `:1238`, `:1241`; `static/js/profile.js:218`.

**Live reproduction:** A, B and C were mutually connected in CS2. A blocked B in GTA. Their own CS2/GTA polls correctly hid each other, and authenticated A's `/api/public-profile?username=B` returned 404. But A's authenticated `GET /profile-squad?username=C&game=cs2` returned **both A and B**, including B's display name, region, city and other public profile fields. C's squad tab therefore still presents B to A. The frontend makes this request with plain `fetch`, omitting its login token entirely, so a backend-only viewer check would not repair the ordinary page journey.

The RPC correctly excludes blocks of the **squad owner C**. It cannot exclude **viewer A's** blocks because this endpoint never supplies viewer identity or filters by it. This is a public-surface consistency/avoidance failure, **not an IGN/Discord leak** or a guarantee of anonymity: the UI already discloses that logged-out people can view public profiles. C's raw mutual count staying at two is not independently a defect unless the product promises viewer-filtered counts.

**Suggested fix:** accept optional authenticated viewer identity on `/profile-squad`, return 404 when viewer and profile owner are blocked either way, and omit squad members blocked either way with that viewer. Use `authFetch` for logged-in public-profile squad loads, retaining anonymous fetch for guests. Cover the three-user graph and cross-game block in API and frontend tests. This pre-existing gap was newly found here; it is not evidence that migration 002 introduced it.

### R4-M02 — Medium: an obsolete Find operation still unlocks a half-loaded game

**Location:** `static/js/ui.js:1503`, `:1509`, **`:1513`**; related stale error at `:1004`–`:1006`.

**Deterministic VM reproduction with the actual registered Find callback and actual `selectGame`:**

1. Click Find in CS2; hold its profile-save request.
2. Select GTA; hold the metadata response. `selectGame` correctly disables Find, changes `state.game`, and has not built GTA's form yet.
3. Reject the old CS2 save. `saveProfile` correctly suppresses its stale error, but the outer `runFind` finally executes `els.btnFind.disabled = !!state.loadFailed`.
4. Observed: **GTA selected, metadata still pending, `hasProfile=false`, Find enabled**. The old operation has released a control now owned by a different generation.

A follow-up harness check, using a collector stub to represent the still-visible CS2 form, captured a second POST to `/api/profile` with **`game:"gta"` and CS2's `mode:"Premier", rank:"Gold Nova"`**. This demonstrates the missing gate; it is not a claim of successful production corruption. The server should reject that particular invalid GTA payload. The independent real-control assertion does not depend on that collector stub.

Another remaining continuation: start CS2 Like, switch to GTA, reject the held Like. The real `handleLike` catch displays **`OLD CS2 LIKE FAILURE`** under GTA. Its timer is now safe, but its error application is not. This error alone is Low; the half-loaded form gate makes the combined generation finding Medium.

**Suggested fix:** capture generation in `runFind`, check it after saving and before scanning, and let finally update controls only if it still owns the current generation. Keep explicit game-loading state in the submission guard, rather than treating `loadFailed=false` as loaded. Guard Like/Like-back/other mutation error rendering with the captured generation too. Add the outer registered handler and rejected-request paths to behavior tests. These are residual paths of R3-M01, not a failure of its repaired scan/timer branches.

## Disagreements with Claude

**H03 severity — accept Medium on reassessment; reject the claimed timing assurance.** I previously rated the post-block private-value disclosure High because it violates contact authorization. Claude is right that the demonstrated exploit additionally needs the victim to block and then change private contact while an old poll spans those operations, making exploitation substantially less reliable than the account-token bugs. Medium better reflects that demonstrated likelihood and scope. I revise that severity; fixing the shared snapshot was still necessary.

However, A can cause and repeat **A's own polls**; A merely cannot guarantee B's two writes land inside them. No enforced or measured “tens-of-ms” limit has been established, and network/database delays can widen the interval. The acceptable argument is lower demonstrated exploitability, not an impossible-to-influence race or a guaranteed tiny window. The new SQL design removes that dispute and is the right repair.

**D4 deferral — accept shipping these correctness/security repairs first; reject treating a scheduled task as completed coverage.** A frontend behavior layer and real PostgreSQL/PostgREST integration are still needed before calling this hardening work complete or prioritizing new product features. The new browser-test files are useful progress: concurrent work added Playwright and a CI Chromium installation step, then landed as `9a3f34e`. They were not present in the tested `0b7ad81` suite, and this review did not independently run or verify that new suite/job. This advances the frontend portion of D4 beyond Claude's round-3 response, but does not prove migration 002, grants or SQL NULL behavior: the new tests' backend still uses `FakeSupabase._social_snapshot`.

The next concrete deliverables should be a mandatory frontend behavior job covering the original R3 interleavings **and the outer Find handler above**, plus a disposable database/PostgREST job applying a self-contained schema and both migrations. Test anon/authenticated denial, NULL legacy rows, cross-game blocks, flag behavior, 600 mutual pairs, and a concurrent block/contact update. Keep it entirely separate from production credentials. I accept the tactical ordering, but D4 stays **not fixed** until those jobs actually run and pass.

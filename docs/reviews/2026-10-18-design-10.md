# Pre-launch design consultation — 2026-10-18

This is design advice for Claude's implementation, not a code review or a claim that the proposed features have passed testing. I read AGENTS.md, the review brief, CLAUDE.md, project history, review 7's product recommendations and response, and the relevant HTML, JavaScript, backend, CSS, migrations and browser-test helpers. References below describe the current checkout. No live accounts were created; there are no test accounts to clean up. No production interaction, database operation, `.env` access, commit or push was performed. This report is the only authored file.

**Recommendation:** build all six user-facing improvements before launch, with smaller implementations for bio storage and the return summary. Reject dual authoritative bio stores, a disappearing shared-player toast, a placeholder support address in final policies, and notification fanout inside profile saves. Keep the existing visual theme. These changes improve the journey, but cannot substitute for an active launch cohort in one game/region/language, as review 7 #1 explains.

## 1. Two-step first game profile

**Agree with the split and one DOM; change the grouping and define “first.”** Use the wizard whenever the selected game has no saved profile, including an existing account adding another game. Editing an existing game stays one form. Determine this from a successful `/api/my-profile` result or its genuine 404, never local storage or a failed load. The current code already distinguishes these cases and protects game loading with `state.gen` and `gameReady` (`static/js/ui.js:469`, `:628`). Do not lose those protections while introducing wizard state.

I would use:

- **1 of 2 — How you play:** region, country, platform only when there is a choice, required game fields, mic and languages. Include short explanations for hard compatibility choices such as LoL server/Minecraft edition. Clearly label required choices. Keep existing valid shared-field prefills.
- **2 of 2 — Connect with squadmates:** show the PlayMate username separately as public identity, with editing only if unclaimed. Offer a recommended game contact and collapsed optional Discord/Steam controls, with “You can save without adding contact details.” Explain that dedicated contact fields become visible after mutual likes. Put city and optional game fields under **More game details (optional)**; city is public matching information, not contact information. Do not silently drop optional BF class/LoL role/other fields merely because step 1 includes only required fields (`buildForm`, `static/js/ui.js:557`).

Hide a single-option platform row but retain its actual selected value in the request. Do not add bio/avatar/banner setup here. Keep “Next,” “Back,” and “Save & Find Teammates”; the final action is available with no contact supplied. A gentle later contact reminder is sufficient. This keeps setup short without requiring Discord membership.

**Username risk:** signup currently records an intended username, while `claim_username` reserves it only on profile save (`static/js/landing.js:133`; `main.py:349`, `:725`). Do not imply it is secured at signup. Validate its format early and say availability is confirmed on save. An availability check is advisory; adding a reservation service is unnecessary for this wizard. A final 409 must focus the username field in step 2 without wiping step 1.

**Save/validation risks:** “Nothing saved until step 2” should mean no profile mutation on Next/Back; Auth signup already exists. Also, today's final POST claims the account separately from the profile upsert (`main.py:794`), so do not promise that a failed final request has absolutely no account-side effects. Keep claims idempotent and recoverable. Validate only the visible step on Next and the complete payload on final submit, routing errors back to the relevant step. Hidden required controls can interfere with native form validation: explicitly control step validation rather than relying on the browser to focus an invisible select. Enter must advance step 1, not call today's save handler directly (`static/js/ui.js:1564`). Disable repeated submission and navigation during the short final save; polling must not reset wizard inputs.

**Acceptance criteria and proof:**

1. New account, adding a second game, and removing/re-adding a game each receive the wizard; saved games open the single editor. A failed profile load shows Retry, never a blank wizard. Test these in Chromium against the fake API.
2. Next and Back issue zero profile writes; values survive Back/Next. One final successful POST creates one user/game row. Double click/Enter, a username collision, invalid optional Steam input, 422, 429 and offline failure preserve all editable values and show the correct step. Prove request counts and final stored payload in API/browser tests.
3. Cover every game template at the validation layer; browser journeys must include single-platform CS2, multi-platform GTA, Minecraft edition, LoL server and optional-role fields. Console/API bypass still receives server validation.
4. New games automatically open the Profile tab on phones; step headings receive focus, progress is announced, inactive steps are absent from keyboard/screen-reader navigation, and errors have text plus `aria-invalid`/descriptions. Test keyboard-only and a screen reader at 375px; check 320px, short landscape and 200% zoom. Use approximately 44px action targets. Existing mobile CSS otherwise starts on Match and hides Profile (`ui.html:14`; `static/css/ui.css:2245`).
5. Hold a load/save response, switch A→B→A, or change authenticated account: an old response cannot advance, populate or mark the new form saved. Account changes must discard the old account's inputs before reload; no private drafts should be persisted as part of this change.

## 2. Bio on match cards

**Agree with `accounts.bio` and a batched lookup; disagree with writing both Auth metadata and accounts on every edit.** That recreates the avatar consistency problem in review 7. `save_account_meta` reads and rewrites the complete PlayMate metadata object (`main.py:394`); two edits to different fields can overwrite each other's old bio, and the Auth update and DB update cannot form one atomic transaction. A successful first write followed by a failed second write creates two believable answers to “what is my bio?”

Make **accounts.bio the only authoritative bio** after migration 008. Backfill once from `raw_app_meta_data.playmate.bio`, validating legacy values rather than assuming all historical metadata satisfies today's API. Add a DB constraint for the agreed length/content rule as well as API validation. Update account GET/PUT, owner editor and public-profile reads together (`main.py:1238`, `:1263`, `:1363`). Stop reading/writing metadata bio in normal operation; an obsolete metadata copy must never resurrect a cleared bio. A migration rerun must not overwrite newer edits or an intentional empty string. Document rollback compatibility rather than keeping permanent dual writes “just in case.”

Require a claimed accounts row for new bio writes, with an explicit 409 before first profile save, as avatar writes already do (`main.py:1277`). Inventory legacy Auth users without an accounts row: preserve any legitimate pre-claim bio through a validated, one-time initialization at claim. Once the new rule is deployed, no concurrent pre-claim bio writer can race that initialization. Do not create an accounts row with an invented username merely to store a bio.

After filtering/ranking and taking the returned 20 candidates (`main.py:995`), fetch only their `user_id,bio` in one accounts query, map internally by ID and enrich one documented response field, preferably `match.profile.bio`. Avoid Auth N+1 calls, fetching all 800 bios, or serializing `accounts.*`. A candidate whose account disappeared should be omitted; a DB failure should produce a controlled error, not silently present obsolete Auth data. This public bio lookup must never alter the mutual-only contact snapshot (`main.py:1073`).

**Card design:** render the escaped full bio with a two-line CSS clamp, wrapping long words, directly under the name. Do not combine a hard 120-character cut with line clamping: they truncate twice, and JS slicing can split emoji. The existing View profile link provides full context. No empty placeholder for players without a bio; no linkification, Markdown or HTML. Keep bio less prominent than name and Looking now, but more useful than decorative space. Two concise compatibility reasons can accompany it; no new profile wizard field is needed.

**Privacy/accessibility/CSP:** tell the editor “Public on your profile and match cards—avoid contact or personal details.” Existing public bios are already publicly readable (`static/js/profile.js:144`); this increases exposure in discovery. The app cannot promise that text voluntarily placed in a bio is private. Escape on every render even though `<`/`>` are rejected. Use existing external JS/CSS and keep the current script CSP (`main.py:68`).

**Acceptance criteria and proof:**

1. API and real-Postgres migration tests cover absent, empty, valid, malformed and overlength legacy values; rerun after editing/clearing; preserve username/avatar/banner/links/referral fields. Explicitly choose one length definition (Unicode code points is consistent with Python) and test emoji at the 280 boundary against the frontend counter.
2. A successful edit/clear agrees on account GET, public profile and a newly fetched deck in every game. Concurrent bio/banner edits cannot restore an old bio. Inject a DB failure and deletion during edit; never return success for a bio write that did not persist or recreate a deleted account. Other-field failures must leave a truthful, recoverable editor state.
3. A populated match response incurs one batch bio query and zero per-candidate Auth lookups; an empty result incurs none. Assert the response contains no IGN, Discord, Steam contact, email, metadata object or newly exposed internal IDs. Blocked users remain excluded; clearing bio does not fall back to metadata.
4. Browser checks cover quotes, ampersands, literal entity-like text, emoji, Persian/RTL text, long unbroken words and newlines. No execution or CSP violation. At 375px and 1366×768, the bio adds at most two visual lines and leaves name, status and Like/Skip usable; full text remains obtainable through View profile with keyboard access.

## 3. Keep the shared player through signup

**Agree with preserving target + game and avoiding an unsolicited redirect; reject a toast as the only return mechanism.** The user's intent was a particular player. Seeing a general deck first is not automatically more valuable. Show a persistent, dismissible context strip during setup and after save: **“You came to connect with @name in CS2”**, then **“Profile saved — View @name”**. Keep it above results, including empty/error results. Do not wait for a successful match scan to offer the return action. Never automatically like the target.

The existing relationship actions already support like/like-back/mutual/incompatible/no-profile (`static/js/profile.js:157`). Reuse them after returning. Update both the hero and game-card links (`:140`, `:167`, `:245`), plus the logged-out `/app` redirect (`static/js/ui.js:1678`); otherwise one path still loses `next`.

Treat this as **validated navigation intent**, separate from referral credit. Parse `next` once and accept only the entire relative path `/u/<username>` using the backend's 3–24-character ASCII username grammar (`main.py:105`). Canonicalize username case and reconstruct the path from the captured username. Reject schemes, hosts, `//`, backslashes, extra path components, queries/fragments, dot-segment usernames `.`/`..`, and encoded/double-encoded separators. Validate again on consumption; local/session storage is untrusted. Validate game against loaded game IDs, not just a permissive regex.

Use one tab-scoped `sessionStorage` object containing target, game, capture time and, after authentication, owner UID. Give it a short documented lifetime, for example 24 hours. Transfer anonymous intent once into the authenticating account, retain it until View/Dismiss, and clear it on logout, account deletion, account switch or expiry. A fresh explicit shared link replaces old intent. Preserve it through auth-cache initialization: current local-storage cleanup deliberately wipes account-owned keys (`static/js/landing.js:30`; `static/js/ui.js:92`). Do not let account B inherit account A's bound intent.

**Important auth edge:** launch is expected to enable email confirmation. Today's `emailRedirectTo` is just the origin (`static/js/landing.js:136`); tab storage will not accompany a confirmation link opened in another browser/tab. Carry the validated, non-secret game/target through an allowed confirmation redirect URL and test the actual Auth redirect allowlist. Do not smuggle it into tokens or override the password-recovery flow. If cross-device continuation is outside v1, say so in the confirmation instructions; same-browser signup/login/confirmation still needs a working path.

**Acceptance criteria and proof:**

1. Browser E2E: shared game → logged-out landing → signup/login → matching game setup → save → persistent target action → current relationship/Like back. Also cover already logged in with/without that game and with an existing saved profile. No first-save requirement may strand a returning player.
2. No link click or auth callback sends a like. Incompatible, deleted, blocked, self-target and removed-game cases show safe current states; contacts remain obtainable only from Squad after a mutual like. The target context survives a match scan failure and a reload within its lifetime.
3. Parameterized parser tests include external URLs, `//evil`, `/u/name/extra`, `%2f`, `%5c`, double encoding, query/fragment suffixes, newline characters, valid dotted usernames and maximum-length names. No external navigation or injected markup; text is escaped and handlers are external JS.
4. Two tabs with different targets stay independent; logout/login as another account clears bound state; old async callbacks cannot consume or display another account's intent. Test confirmation in a fresh tab and ensure password recovery still stays in recovery mode.
5. The context strip is keyboard reachable, readable on phones and does not cover sticky Like/Skip. Today's toast container has `pointer-events:none` (`static/css/ui.css:1537`), another reason not to turn the current toast into the sole clickable workflow.

## 4. Saved / unsaved game preferences

**Agree, but dirty state must describe persisted preferences, not DOM differences.** Use one canonical serializer for the effective profile payload and its saved baseline. Sort language sets and field keys, normalize whitespace/nulls, use canonical Steam paths, and exclude search filters, wizard step, Looking now, activity, avatar and UI state. Filters are not saved profile preferences (`ui.html:203`; `static/js/ui.js:705`). An unsupported hidden Steam field must not remain secretly dirty; changing PC to console is itself a meaningful edit and saving uses the server's contact-clearing behavior.

Initialize the baseline only after server loading and dependent-select prefills finish. A new prefilled profile says **“Not saved yet”**, not “Saved”; do not show a discard warning just because defaults/prefills appeared. Track subsequent meaningful edits across both wizard steps. Returning profiles show **Saved ✓ / Unsaved changes / Saving… / Couldn't save—changes kept**, with text, not just button color. Use “Save changes” for existing profiles and keep “Find teammates” as a scan action when clean; dirty scan actions must explicitly save first or explain that results use saved preferences. Do not let a clean Scan rewrite the profile unnecessarily; today's `runFind` always saves (`static/js/ui.js:1571`).

On a successful POST, establish the baseline from the server-normalized saved DTO, not the raw submitted values (`main.py:746`, `:752`, `:778`). Simplest v1: disable the preference fieldset, wizard navigation and game switching during the save, then re-enable on success/failure. Otherwise a held request can overwrite a newer edit and falsely show Saved. Save success and subsequent scan failure are separate outcomes: keep Saved when matching fails.

Guard actual game selection **before** `selectGame` closes/reset state or changes URL/local storage (`static/js/ui.js:469`). A native confirmation is sufficient: “Discard unsaved changes to CS2?” Cancel leaves game, inputs, step and URL intact. Merely opening/canceling the picker or switching mobile tabs must not warn. Intentional logout may ask once before proceeding; automatic auth/account changes must clear private state and reload without trapping the user on the old account. Do not interfere with account deletion.

Attach the dirty `beforeunload` warning only while needed. It is a fallback: browsers control the prompt, and mobile termination may bypass it. Do not promise recovery or add private contact autosave to local storage as a workaround. The existing unload listener also stops realtime (`static/js/ui.js:1663`); canceling navigation must leave polling working. See the [HTML navigation standard](https://html.spec.whatwg.org/dev/browsing-the-web.html) and [Chrome's page lifecycle guidance](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).

**Acceptance criteria and proof:**

1. Table-driven canonicalization tests: reordered languages, equivalent Steam input, trimmed values, null/empty, dependent country/city reset and edit-then-revert. Browser assertions: loading/prefill/filter/Looking-now/poll changes never falsely mark a saved profile dirty; real field/language-pill changes do.
2. Hold save; try typing, Enter, game switch and mobile Back. Only one request is sent, intended values persist, controls recover after success/422/429/network failure, and a late response cannot mark another game/account Saved. A failed scan after a successful save leaves Saved visible.
3. Cancel/accept game switch and normal page navigation; clean forms never warn, dirty forms warn once. Picking the current game does not discard anything. Canceling browser navigation keeps polling alive. Test actual browser dialogs with user activation, plus manual mobile checks acknowledging OS-close limitations.
4. Status has a polite live region, does not announce every keystroke, remains readable at 200% zoom, and is visible near Save on phones. No new inline scripts/handlers or CSP relaxation.

## 5. Final Terms and Privacy

**Rewrite them, but reject the proposal as launch-ready while support remains a placeholder.** A domain is not necessary for a monitored support mailbox. Use a real address now, then migrate it later. Identify the operator and a working privacy/safety contact; only the owner can supply the truthful identity, operating jurisdiction and provider configuration. These are inputs Claude must obtain before calling the text final, not facts to invent. This consultation is not legal clearance for a worldwide launch.

Correct these specific claims before polishing prose:

- **Visibility:** list public identity, bio, links, per-game fields including optional city, activity/Looking now and public squad information. Dedicated IGN/Discord/Steam fields are owner/mutual-only, but someone can publish contact information in their public bio/links. Blocking hides profiles from the authenticated blocked account; it cannot prevent anonymous access or copied screenshots (`main.py:1347`). Mutual contacts already copied into another app cannot be recalled by unmatching.
- **Storage:** “cookies = only local storage for the session” conflates technologies and duration. Supabase sessions and `pm_access_token`, shared profile/contact cache, game selection and referrals use persistent local storage; skipped players/auth continuation use session storage (`static/js/ui.js:73`, `:189`, `:781`; `static/js/landing.js:19`, `:46`). Inventory the deployed browser and provider behavior. State actual purposes/lifetimes; do not claim “session only,” “no tracking” or a cookie-consent exemption without that evidence. Third-party Supabase/unpkg requests and hosting/Auth operational logs also deserve consideration.
- **Deletion:** current successful deletion removes active application rows and Auth login, but the two operations can fail separately (`main.py:1298`). Reports currently disappear when either involved account is deleted; they are not an independent retained moderation record. Do not promise all copies/backups/logs disappear instantly or reports survive deletion. Confirm actual backup/log retention with provider settings; distinguish active deletion, residual retention and third-party copies. New bio/watch data must be included in deletion. Provide a usable support path for the existing partial-failure message.
- **Age:** “13, 16 in the EU” is not a universal legal rule. The EU consent threshold varies by Member State and concerns consent-based processing; it is not simply a continent-wide minimum signup age. See the [European Commission's explanation](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/legal-grounds-processing-data/are-there-any-specific-safeguards-data-about-children_en). Choose an explicit service eligibility policy and implement matching signup text/age handling; do not collect full birth dates or identity documents by default. A declared age floor alone does not settle child-safety duties. Plan a response to underage reports/actual knowledge; the [FTC COPPA FAQ](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions) explains why merely prohibiting children in Terms is insufficient in relevant cases.

Keep Terms and Privacy distinct, dated and navigable even if served from one HTML file. Terms should cover acceptable use, reports/moderation, suspension, no endorsement/rank verification, external contact services, service limitations and changes; avoid a blanket “we may do anything” clause. Privacy should explain purposes, data categories/visibility, matching, recipients/providers, actual retention, applicable rights/request process, transfers and safeguards where applicable, and optional notification choices. Do not substitute “Supabase/Render are processors” for this inventory. The [ICO's privacy information checklist](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/the-right-to-be-informed/what-privacy-information-should-we-provide/) is a useful scope check where UK GDPR applies; applicable law depends on the operator and audience.

“We do not sell personal data” is reasonable only as a verified present practice. Do not advertise future email alerts or retained report evidence before those features exist. Explain what reporting actually does and how to ask for help, without promising response times the owner cannot maintain. At signup, distinguish agreement to Terms from acknowledgement of the Privacy notice; do not bundle optional alerts into acceptance (`landing.html:145`).

**Acceptance criteria and proof:**

1. Owner completes a data/retention/provider/age/support fact checklist; every policy claim maps to current behavior or a confirmed configuration. No placeholders, draft badge, invented retention period or unsupported legal assertion remains. Verify support can receive an ordinary message using the owner's normal process; no automated message was sent in this consultation.
2. API/browser tests exercise logged-out public visibility, nonmutual/mutual contacts including Steam, block/unmatch, game removal, full deletion and injected Auth-deletion failure. Assert new bio/watch data cleanup. Verify reporting/deletion wording against actual report lifecycle. Review provider logs/backups separately; tests cannot prove physical erasure there.
3. `/terms` and `/privacy`, their section anchors, signup and Settings links work logged out, on keyboard/mobile and with JS disabled. Current `/privacy` relies on JS scrolling (`static/js/legal.js:1`); provide a visible in-page contents link even without JS. Check phone access to both policies: `landing.css:555` hides header links. Use correct page titles, heading hierarchy, readable contrast and no horizontal overflow.
4. Email-confirmation signup, login, reset, deletion and real support access are part of the launch rehearsal. Policy publication does not complete the already recorded email-confirmation launch gate.

## 6. Better empty state and a return summary

**Improve the empty state now; reject “Notify me” for an in-app-only feature and reject save-time recipient fanout.** Nothing reaches a player who closes PlayMate. Browser notifications currently depend on an open app (`static/js/ui.js:1500`), and a database notice does not change that. Use **“Show players when I return”** with **“In-app only. No email or push yet.”** Do not collect an email preference you cannot honor or silently convert this opt-in into email consent later.

First fix the explanations. The current filtered empty state says filters *are* hiding players without checking whether any exist (`static/js/ui.js:839`). Distinguish loading failure, incomplete profile, more batches, everyone skipped/liked, no hard-compatible candidates, and optional filters yielding no results. Say “Try removing filters,” unless the server actually proved alternatives exist. Never suggest changing GTA platform, LoL server or Minecraft edition simply to make the pool look bigger. Looking now boosts visibility; it does not summon players or guarantee a teammate. Do not advertise another game as populated without evidence.

**My smallest pre-launch version:** one server-owned opt-in flag on the user's game profile, default off. On return to that game, perform an on-demand eligible-candidate check and show **“Players available to check in CS2” → “Find teammates.”** No exact “2 new since your last visit” claim, unread counter, events table, worker or new-profile fanout. This deliberately promises current availability, not delivery or an arrival history. Explain this scope to the owner: it improves the return experience but does not solve review 7's durable return-channel problem. It is what I would ship before launch; email/push can later supply the actual “tell me when someone joins” function.

Use the current saved profile and shared backend eligibility rules: same game, hard crossplay/edition/server compatibility, blocks both ways, self excluded, outgoing likes excluded. Region/language are soft scoring preferences unless explicitly filtered (`main.py:896`, `:972`). State whether optional current filters apply; I recommend the return check ignores transient Looking-only/language filters and labels that clearly. Session skips should not redefine server eligibility. A positive check means there is a usable next action, not that a person is online or ready to respond.

Keep the check read-only and free of contacts; cap/stop after finding one eligible candidate, not after finding one raw profile. The current matching query inspects a bounded 500+300 pool (`main.py:956`), so if reused, an empty answer is “No players found right now,” not proof that the whole game has none. Share predicate code without running an unbounded per-subscriber scan on every profile save. Check once on game entry/return with a modest freshness interval; do not add a second 15-second poll loop. If availability is stale or errors/429 occur, keep a neutral Find action and Retry-After behavior rather than presenting zero.

**If the owner requires exact new-player notices before launch:** that is a larger design than a flag. Specify first committed user/game enrollment versus edits, distinct candidates, current eligibility, delivery/seen/acknowledged states and preference changes before choosing a schema. Generate a digest on read rather than synchronously notifying all subscribers during profile save. A stored event must not retain a blocked/deleted player's name or contacts in a visible notice. Revalidate eligibility at read. Ack only a successfully presented snapshot on an explicit scan/dismiss, monotonically across tabs; opening the page or a failed scan must not clear it. Ordinary profile edits, ping and Looking now must not count as new joins. A raw counter increment and `last_active` watermark cannot satisfy this. Even a `created_at` cursor needs a delayed-commit test: a transaction begun before a cutoff can become visible after acknowledgment. Exact delivery needs a proven snapshot/cursor protocol, not client-clock timestamps. This added state is why I recommend the availability version above.

**Acceptance criteria and proof for the recommended version:**

1. Opt-in/out is idempotent, authenticated, UID-derived and rate-limited; another user cannot read/change it. RLS prevents direct browser table access. It survives reload/device changes, remains off for other games, and is removed with the game/account. Include real-Postgres FK/deletion tests; a late preference write cannot recreate a removed profile/account. Profile saves must preserve the flag when omitted.
2. API eligibility matrix: GTA platform split, FC Switch, Minecraft edition, LoL server, both block directions, self, liked player, soft region/language differences and missing game profile. A compatible QA enrollment appears on the next successful check; an ordinary edit does not manufacture a “new” claim. Deleted/blocked candidates disappear on the next check. No contact fields, names of excluded players or false exact counts are returned.
3. Browser: double opt-in/out, 429/offline, page hidden→visible, A→B→A and account switch with a held response. Old results cannot change the current game's opt-in/summary. Opt-out during an outstanding check suppresses its eventual summary. Saving a new compatible profile is not coupled to alert delivery success.
4. Empty-state tests include real zero, filtered zero, skipped batch, outgoing-like exhaustion, `has_more`, server error and stale positive availability. Copy must match known facts. Find revalidates live results and handles a player disappearing between check and click gracefully.
5. Phone/keyboard/screen-reader users can opt in, find players and disable the feature without a modal maze; state changes are announced once. Use one primary next action and at most two secondary alternatives. No Notification permission prompt, new external script, inline handler or CSP expansion.

## Build order and launch decision

| Order | Work | Why this order |
|---|---|---|
| 1 | Settle policy facts, operator/age policy and working support; start #5 | These are launch blockers and require owner facts. Draft now; reconcile final wording after all six implementations. A domain is not a prerequisite for support. |
| 2 | #4 canonical form/save state and discard handling | This supplies the reliable baseline, save lock and navigation rules the wizard needs. |
| 3 | #1 two-step setup | Build on those rules; cover every game template and the phone flow before adding target continuation. |
| 4 | #3 shared-player continuation | Completes a concrete acquisition→setup→specific-player journey; include email confirmation now. |
| 5 | #2 authoritative bio migration and card | Independent, small user benefit once migration/read paths are consistent. Run migration CI before deployment and never deploy readers before their required schema exists. |
| 6 | #6 honest empty state + opt-in availability on return | Ship useful return UX with no save-time fanout or notification infrastructure. |
| 7 | Final #5 reconciliation and all-page rehearsal | Policies, support, Settings, public profiles and empty/error/mobile states must match the finished product before launch. |

**Not worth doing before launch:** exact arrival counters, event fanout/notification workers, a general notification center, draft autosave of private contacts, username reservation infrastructure, or a visual redesign. Email/push delivery should wait for a configured sender/channel and explicit preferences, but do not describe its absence as solved by an in-app notice. These are scope reductions within the six improvements, not permission to launch with draft pages or dead controls.

Use existing fake-DB/API tests for payload/authorization/failure contracts, held-fetch Chromium tests for navigation/save races, and the real Postgres/PostgREST CI job for migrations, constraints and deletion/concurrency. Existing browser contexts bypass CSP (`tests/browser_support.py:81`), so add/retain an explicit production-CSP run; a green ordinary browser suite cannot establish CSP compatibility. Add a short real Safari/iOS and Android Chrome rehearsal for keyboard, viewport, Back and auth confirmation. Finish with all supported pages and all game templates usable, required CI green, verified support and policy facts, and seeded responsive players for the chosen launch cohort. No launch until that gate is met.

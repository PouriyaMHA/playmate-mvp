# Review 11 — six pre-launch improvements

**Verdict: changes need another revision; not ready for public launch.** The normal acquisition → profile → specific player → mutual squad journey works live. Save locking, account pinning, stale-response guards, contact privacy and the authoritative bio store are substantial improvements. However, several acceptance criteria fail, including lost wizard edits, hidden mobile continuation context, confirmation-link ownership/expiry handling, and successful responses to bio writes that did not persist. The support contact remains an acknowledged launch blocker. No new Critical or High security issue was demonstrated.

Reviewed checkout: `9cc5e59a98fbbbedf47929735afa3d52cde1536b`. Read AGENTS.md, the review brief, CLAUDE.md, project history, and the complete design-10 consultation including Claude's response. Deployed `ui.js`, `landing.js` and `profile.js` match the checkout after line-ending normalization; deployed `ui.css` matches byte-for-byte.

## New findings

### F1 — Medium: wizard edits are unprotected on step 1, including after Back

**Location:** `static/js/ui.js:788–791`, `:548`, `:1884–1887`.

`isDirty()` returns `state.wizard && state.step === 2` when there is no saved baseline. It never compares new-profile edits to initial prefills. Live: fill step 1 → dirty false; Next → true; enter contacts → Back → false. Additional Chromium probe switches games from this edited step 1 without any confirm. Inputs are discarded; unloading has the same missing protection. Conversely, merely advancing to step 2 marks untouched prefills dirty.

**Fix:** retain a separate initial canonical snapshot for new forms, compare actual edits across both steps, and keep “Not saved yet” distinct from dirty. Include username in new-profile edit tracking. Test edit → Next → contacts → Back → cancel/accept switch and reload.

### F2 — Medium: shared-player context disappears during mobile setup

**Location:** `ui.html:247–248`; `static/css/ui.css:2247–2254`; `static/js/ui.js:608`.

The context is inside `#match-panel`; phone setup deliberately selects Profile and CSS hides Match. This fails the reason for the persistent strip at the most important acquisition moment. Text existing in the DOM is insufficient; live visibility is false.

**Fix:** put the single strip above the mobile panel switch, or render it in the active setup/results region with one consistent dismiss/view state. Assert visibility, not only `inner_text`, throughout both wizard steps at 375/320px.

### F3 — Medium: confirmation URLs can resurrect expired or another account's intent

**Location:** `static/js/landing.js:40–46`, `:163`; contrast `static/js/ui.js:229–246`.

`intentQuery()` checks target syntax only. It does not check `uid` or the 24-hour TTL. Reproduced with an intent bound to account A and timestamp 48 hours old: it returns `?game=cs2&next=%2Fu%2Fqatwo`. Opening that URL in a fresh tab captures a new timestamp and no UID. Confirmation as B can now bind A's target to B. Ordinary same-tab `readIntent()` rejection does not protect this path. A tab resting on a legal page during logout elsewhere can retain such session storage.

**Fix:** expire/clear stale or previously bound intent before unauthenticated signup continuation; explicitly carry only the anonymous intent belonging to the current signup attempt. Centralize validation for capture, storage consumption and confirmation construction. Test account A → logout on another surface → B signup → fresh-tab confirmation, plus expiry. This exposes shared-target context, not private contacts or an external redirect.

### F4 — Medium: bio deletion races violate read/write success contracts

**Location:** `main.py:1331–1338`, `:1036–1037`.

After account existence is checked, deletion can remove the accounts row before the bio UPDATE. Its returned rows are ignored. In the application's existing data-delete → Auth-delete gap, a fake-DB interleave returns **200, bio empty, username null, games empty** for a requested `new bio`; nothing persisted. This also applies when Auth deletion fails and leaves a login. Separately, removing a candidate's account during the batched bio read still returns that candidate with `bio=''` instead of omitting it. Both interleavings were reproduced without production fault injection.

**Fix:** require a returned updated accounts row and fail explicitly when it disappeared; never upsert to repair deletion. Filter disappeared-account candidates from the returned page and keep totals/page semantics truthful. Add deterministic deletion-interleave tests and Postgres coverage for the write contract.

### F5 — Low: the bio editor accepts only 140 emoji despite a 280-code-point API limit

**Location:** `profile.html:86`; `static/js/profile.js:319,408`; `main.py:1305–1307`.

The API accepts 280 game-controller emoji. Normal Chromium typing stops at **140 emoji**, with `280/280` displayed, because `maxlength` and `.length` count UTF-16 units. Programmatic filling is not proof of the actual typing limit.

**Fix:** use code-point counting (`Array.from(value).length`) and matching input/paste validation rather than HTML's unit-based 280 maxlength. Preserve complete characters. Test typing/pasting and editing a 280-emoji bio loaded from the API.

### F6 — Low: Enter does not submit the profile

**Location:** `ui.html:234–240`; `static/js/ui.js:1775–1797`.

All action buttons are `type=button`. With multiple text inputs, browser implicit form submission does not occur; the submit listener therefore does not make Enter work. Live step-2 Discord Enter leaves `hasProfile=false`; local request recording confirms zero profile POSTs. Synthetic submit events do not test this behavior.

**Fix:** provide a real submit action and route it through the existing single-flight/step logic; keep Back as a button. Test actual keyboard presses, including step 1 where applicable, final save and repeated Enter while held.

### F7 — Medium: new wizard validation lacks programmatic error semantics

**Location:** `static/js/ui.js:897–907`; `ui.html:125–128`; generated field labels at `static/js/ui.js:653–660`.

Validation adds CSS classes and a transient summary toast but no `aria-invalid` or field-specific error description. Browser probe of invalid Minecraft shows platform/edition/mode/style all with null invalid/description attributes. Required status is not consistently presented to users (notably languages/platform). The step counter is not an announced progress region, and initial setup does not focus the heading; only later Next/Back do.

**Fix:** associate durable text errors with controls, mark/reset invalid state, label required groups, and make step title/progress announcement intentional on initial entry and transitions. Verify with an actual screen reader; DOM attributes alone will not establish usable announcements.

### F8 — Low: canonical/save-error state still produces false warnings

**Location:** `static/js/ui.js:781–807`, `:858–872`, `:1798–1801`.

Saved Steam URL `https://steamcommunity.com/profiles/76561197960287930` changed to the equivalent ID `76561197960287930` becomes dirty, despite persisting the same canonical contact. This triggers an unnecessary save/discard warning. Separately, after a failed save, reverting to the saved mic leaves “Couldn't save — your changes are kept” even though the action is clean Find; `saveError` always wins over clean state. Both reproduced.

**Fix:** canonicalize accepted Steam representations for comparison; handle invalid text separately. Clear/suppress obsolete save errors when the form returns to baseline, while preserving a meaningful failure message for genuinely unsaved values.

### F9 — Medium: empty-state counts do not always justify their promised recovery

**Location:** `main.py:978–1011`; `static/js/ui.js:1041–1067`.

**Repro A:** my saved language is fa; the only eligible QA candidate speaks en; skip them, then turn Same language only on. Because skip counting happens before language filtering, UI says “See the 1 player you skipped.” Clicking it yields **zero players**, then “Your filters hide everyone.” The proposed single recovery action could never work under current filters. Looking-only has the same overlap.

**Repro B:** fake pool contains 500 recent incompatible GTA rows and an older compatible one beyond the scan. API returns `matches=[]`, `incompatible=500`, `has_more=false`. UI declares no one can team up yet and describes all players as incompatible, although a compatible profile exists. “New players join every day” is also unsupported by these counts.

**Fix:** compute actionable overlapping categories or explicit counts for each proposed recovery under the remaining predicates. Expose bounded/truncated search status and use “No players found in this scan” when completeness is unknown. Avoid whole-population/daily-growth claims. This does not require exact arrival counters or a notification system.

### F10 — Low: the new policy inventory still omits material visibility/choice detail

**Location:** `legal.html:94–101`, `:130–136`, `:147–166`; `static/js/ui.js:1708–1724`.

The public-profile list omits last-active/Looking-now and public squad relationships. Activity is listed as collected, alongside private blocks/reports, without clearly explaining which activity is public. The policy also omits the existing optional open-app browser notification behavior and does not distinguish persistent local storage, tab session storage and the target's 24-hour expiry. These were explicit design requirements, not a request for invented retention periods.

**Fix:** reconcile the inventory with actual public endpoints and browser behavior, distinguishing visibility and lifetimes. Have the owner confirm operational/provider facts and supply a monitored contact before describing these documents as final. No legal-compliance certification is implied by this code review.

## Disagreements with Claude

1. **#6: I accept part of the simplification, not equivalence to the proposed return feature.** A checkbox merely enabling a scan that already runs on game entry adds little, so I would not insist on that control for its own sake. Claude is right that neither it nor an in-app summary reaches someone who closes the app. But the proposed check deliberately ignored transient filters/skips and covered return to the experience; current visibility handling only polls social state, and the new empty-state counts have the failures in F9. Call the delivered work “better empty states,” not completed return availability or notifications. The owner should explicitly choose the reduced scope. If return availability remains required, implement one fresh, actionable availability indication using shared eligibility, without a second poll loop or save-time fanout. Email/push remains separate; obtaining a sender/domain does not replace preferences or consent design.
2. **#4's canonical/save-state claim is overstated.** Step number is not a canonical draft baseline, and raw Steam text is not canonical Steam identity. F1/F8 are concrete counterexamples. Save locking and generation checks are good and should be retained.
3. **#3 is not yet fully account-bound or persistent on phones.** App consumption is protected, but email-link construction bypasses those protections; a hidden strip during setup does not satisfy persistent visible context. Fix F2/F3 before treating this done.
4. **#2's store design is accepted; boundary/deletion contracts are unfinished.** Keeping bio out of metadata writes solves the important overwrite problem. A DB constraint does not reconcile browser UTF-16 limits, nor make a zero-row UPDATE a successful edit.
5. **#5 remains a launch blocker by mutual agreement.** The address placeholder is openly acknowledged, which is preferable to inventing an address. A domain is not necessary for a monitored support mailbox. The owner still needs to verify the facts and actual receive path; policy publication alone is insufficient.
6. **Correction to my design consultation:** LoL role is required in current `games.py`, not optional. Keeping it in step 1 is correct for that schema. BF class is the tested optional example. This correction does not excuse missing optional fields in any template that actually marks them optional.
